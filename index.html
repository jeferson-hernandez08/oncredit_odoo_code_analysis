Análisis de Diferencias: Código vs Base de Datos de Producción

Proyecto: GrupoSomos EPM

Comparación entre el módulo de código fuente (custom/theme_somos) y el export de la base de datos de producción (export_views/theme_somos)

Odoo 16 Fecha análisis: 25 - Marzo - 2026 Backup BD producción: 03 - febrero - 2026 Análisis Realizado Por: Jeferson Hernandez
1. Contexto del Análisis
⚠️ Situación actual identificada El proyecto portal_somos_theme_somos (También llamado renombrado como theme_somos) inició con desarrollo desde código fuente (este repositorio), pero a mitad del proyecto la continuación se realizó directamente desde la plataforma Odoo (edición en base de datos de producción). Esto generó una brecha importante entre el código fuente y el estado real del frontend y backend en producción. ⚠️ Nota Importante de cópia backup BD producción Este análisis de código es realizado sobre la base de datos backup de producción extraida de la fecha: 03 - febrero - 2026
ℹ️ Objetivo de este documento Documentar de forma exhaustiva todas las diferencias entre los archivos XML del módulo theme_somos en código fuente vs. los exportados de la base de datos de producción, para apoyar la toma de decisiones técnicas del equipo GrupoSomos EPM.
📁 Fuente A — Código Fuente

custom/theme_somos/

Módulo Odoo desarrollado desde código. Contiene vistas, datos, seguridad, controladores y assets. Punto de partida del proyecto.

🗄️ Fuente B — Base de Datos de Producción

export_views/theme_somos/

Export de las vistas XML almacenadas en la BD de producción. Refleja el estado actual real del sistema tal como fue modificado desde la plataforma Odoo.

8. Diferencias Estructurales entre Código y Base de Datos
📁 Estructura del Código Fuente (custom/theme_somos)
  • __manifest__.py — Declaración del módulo
  • __init__.py + exceptions.py — Python
  • controllers/ — Controladores HTTP
  • models/ — Modelos de datos Odoo ORM
  • views/ — Vistas XML (template QWeb)
  • views/pages/ — 55 páginas del sitio
  • data/ — Datos iniciales XML
  • security/ — Reglas de acceso
  • static/ — Assets (CSS, JS, imágenes, fuentes, videos)

✅ Estructura completa de módulo Odoo con separación de responsabilidades. Incluye modelos Python, controladores, y datos semilla.

🗄️ Estructura del Export de BD (export_views/theme_somos)
  • 40 archivos .xml planos (sin subcarpetas)
  • Solo contiene registros ir.ui.view
  • Sin controladores, modelos, ni assets
  • Sin archivos de seguridad o datos iniciales
  • Representan el estado actual de las vistas en BD
  • Estructura <record model="ir.ui.view">
  • Nombrados con prefijo page_ o somos_

⚠️ Export parcial: solo vistas XML. No incluye modelos Python, controladores ni assets estáticos. Es solo la capa de presentación.

⚠️ Export de módulos: En la exportación de la base de datos backup producción contiene 20 módulos incluyento theme_somos.

9. Recomendaciones Técnicas
✅ Plan de acción recomendado para sincronización (Si se Desea Realizar Migración a Código Fuente) Basado en el análisis, se propone el siguiente orden de trabajo para alinear el código fuente con la base de datos de producción.
PrioridadAcciónArchivos InvolucradosImpacto
🔴 1 — Alta Incorporar al código fuente los 14 archivos nuevos de BD que no tienen respaldo en código header.xml, footer.xml, page_canal_transparencia.xml, page_gestion_cobranza.xml, wolkvox_script_addition.xml, page_campain_update_user.xml, page_requirement-pqrs_wolkvox.xml y 7 más 🚨 Crítico: sin esto, el código no refleja producción
🔴 2 — Alta Actualizar los 23 archivos renombrados para alinear naming convention (page_ prefix) Todos los archivos de la sección 4 de este documento Alto: inconsistencia de nombres entre BD y código
🔴 3 — Alta Incorporar aproximadamente 20 módulos adicionales necesarios para completar la funcionalidad del sistema Módulos personalizados y dependencias detectadas durante el análisis 🚨 Crítico: el sistema no funcionará completamente sin estos módulos
🟡 4 — Media Revisar archivos solo en código y decidir cuáles se eliminan, cuáles se mantienen como backend, y cuáles se actualizan collection_management.xml, complaints_channel.xml, otp_register.xml, allies.xml Medio: limpieza de código y deuda técnica
🟡 5 — Media Sincronizar el contenido de las páginas: comparar línea a línea las versiones de código y BD para identificar cambios de contenido Las 23 páginas con equivalente en ambos lados Medio: asegurar que código = producción
🟢 6 — Baja Establecer un flujo de trabajo GitOps: código → review → deploy a producción. Nunca editar directamente desde la plataforma Odoo Todo el proyecto Preventivo: evitar esta situación en el futuro
10. Conclusiones
📌 Hallazgos Principales
  • El código fuente tiene 64 XML vs 40 en BD — pero menos páginas únicas reales por diferencia de naming
  • 23 páginas existen en ambos lados con diferente nombre y contenido modificado
  • 14 páginas/componentes nuevos en BD que no tienen respaldo en código (riesgo de pérdida)
  • 30 archivos en código sin equivalente en BD, mayormente vistas de backend/admin
  • La BD de producción tiene 787 archivos XML en total (20 módulos) vs 81 en código personalizado
  • Se incorporaron integraciones nuevas en BD: Wolkvox chat y PQRS Wolkvox
  • El header y footer fueron refactorizados como componentes independientes en BD
  • Nuevas páginas legales: Canal de Transparencia, Política de Tratamiento de Datos
  • Nueva funcionalidad: Vacantes / Trabaja con Nosotros, Gestión de Cobranza
🎯 Riesgo Técnico
  • 🔴 El código fuente está desactualizado respecto a producción
  • 🔴 Hacer un deploy desde código sobreescribiría cambios de producción
  • 🔴 Los 14 archivos nuevos de BD no tienen backup en código — riesgo si la BD se daña
  • 🟡 Existe inconsistencia de naming entre BD y código que complica la sincronización
  • 🟡 La integración Wolkvox (chat + PQRS) solo está en BD
  • 🟢 Los modelos Python, controladores y assets estáticos del código fuente aún son relevantes y necesarios
